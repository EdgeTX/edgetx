Mambo controller-application flashing
====================================

This uploader uses the ORIGINAL TBS USB HID bootloader. It updates only the
EdgeTX controller application at 0x0800C000..0x080C0000; it never sends a
bootloader/internal-RF update, reset, flash-unlock or readout command.

Back up your SD card, models/settings and your radio's own
/CROSSFIRE/EEPROM.bin before testing. Know how to reinstall stock FreedomTX
using TBS Agent before the first installation. This tool does not back up
installed firmware, bundle stock firmware or provide an arbitrary-image
restore mode. Do not replace the TBS bootloader or update the internal RF
as part of this application test.

Requirements
------------
- Python 3.10+ and pyelftools (included in the repo's `uv sync` dependencies).
- A native HIDAPI 0.14+ shared library for live probe/flash. On macOS it can
  be installed with `brew install hidapi`. Use MAMBO_HID_LIBRARY (CMake) or
  --hid-library (direct CLI) to select an explicit library path if needed.
- A matching Mambo firmware.bin AND symbol-bearing firmware.elf. Both are
  generated by the firmware build; the binary alone is insufficient.
- A USB data cable and the radio in its controller bootloader mode.

Earlier versions of this transfer logic have been hardware-tested on macOS
with one Mambo. The public extraction is covered by simulated tests; live
hardware testing of this exact entry point is still required. Linux requires
native hidraw access permissions, and Windows a matching HIDAPI DLL. Neither
Windows nor Linux is hardware-qualified here. Do not detach/replace USB
drivers, change option bytes or disable readout protection to use this tool.

Repo build and offline preview (no USB access)
---------------------------------------------
Using the ordinary EdgeTX build environment, from the repo root:

  cmake --preset mambo -DLUA=ON -DLUA_COMPILER=ON -DLUA_MIXER=ON
  cmake --build build/mambo --target flash-plan

flash-plan builds the default Mambo firmware, verifies ELF/bin correspondence,
flash/SRAM/CCM reservations and external-bay interrupt vectors, and prints
the image SHA256. It does NOT open HID, query devices, erase, upload or create
transfer logs. Review the image/build before approving the displayed hash.

Find the controller serial (USB discovery only)
----------------------------------------------
Close Agent/other USB tools. Turn the radio OFF, disconnect USB, hold PAGE,
then connect USB while holding PAGE until bootloader mode is established.
Use PAGE, not MENU (the latter selects the internal RF updater).

  cmake --build build/mambo --target flash-probe

This explicitly opens HID and sends only the device-discovery ping. It checks
the HID descriptor, TBS BOOTLOADER name, hardware 00041001 and protocol 1, then
prints the controller's numeric serial. It never sends an erase header.
The tool refuses zero/multiple matching HID interfaces; connect one radio.

Flash the reviewed build (explicit application erase)
----------------------------------------------------
Set the serial from flash-probe and hash from flash-plan for this invocation.
The following are placeholders: replace BOTH values before running.

macOS/Linux shell:

  MAMBO_FLASH_SERIAL=SERIAL_FROM_PROBE \
  MAMBO_FLASH_SHA256=SHA256_FROM_PLAN \
  cmake --build build/mambo --target flash

PowerShell:

  $env:MAMBO_FLASH_SERIAL = 'SERIAL_FROM_PROBE'
  $env:MAMBO_FLASH_SHA256 = 'SHA256_FROM_PLAN'
  cmake --build build/mambo --target flash

These are build-time environment variables, not configure-time options. A
changed/rebuilt image must get a new preview and SHA256 approval. Missing or
invalid pins fail before HID is opened. Device identity is queried/checked
again before the one erase-triggering application header is sent. There is
no automatic serial selection, hash approval, re-erase, reconnect or resume.

Keep USB connected until BOTH the terminal checksum and DownloadFinished are
received. Success is protocol completion, NOT flash readback, a cryptographic
signature check or proof of startup/flight safety. No reboot command is sent.
Disconnect USB, boot on batteries and check startup, encoder/Hall inputs,
external-bay Off/CRSF behavior and shutdown. Use a bench, not a flying model.

Each live run gets a fresh directory below build/mambo/mambo-flash-logs with
plan.json, events.jsonl, usb.jsonl and, only on completion, result.json. These
are local build outputs; do not commit them. Existing log directories are
never overwritten. The updater requires 64 MiB free for logs before USB access.

Standalone CLI / downloaded CI bundle
------------------------------------
CI packages firmware.bin, firmware.elf, the uploader/verifier, this guide,
LICENSE, SOURCE_REVISION.txt and flash-plan.json. Extract the bundle and run
the following from its directory (Python/pyelftools/HIDAPI are still needed):

  python3 mambo_flash.py --image firmware.bin --elf firmware.elf
  python3 mambo_flash.py --probe
  python3 mambo_flash.py --image firmware.bin --elf firmware.elf \
    --expected-serial SERIAL_FROM_PROBE --expected-sha256 SHA256_FROM_PLAN \
    --log-dir logs/test-1 --execute

Without --execute or --probe, the CLI is an offline verifier only. Probe and
execute modes cannot be combined. No firmware/RF profile selector exists.
The default data pacing is 20 ms per chunk; --chunk-delay-ms accepts 10..100.
The CMake targets deliberately use the default pacing.

Failure / recovery
------------------
If an error occurs after an erase-triggering write was attempted, the
application may be incomplete. Do NOT try normal startup. Keep the radio in
the controller bootloader and preserve the logs. Fix the connection/disk
problem, and cold-reconnect using PAGE before deliberately starting another
full, verified application transfer or using the stock TBS recovery workflow.
The tool never changes bootloader/RF flash to attempt recovery. An interrupted
transfer is not automatically resumed or erased again. There is no guarantee
of recovery from every possible hardware/bootloader fault.
